# EQ 证据分级

本文集中整理 SoundSticks 5 七段均衡器的协议、HK One 2.5.4 前端行为及第三方实现边界。
事实优先级仍以仓库根目录的 [FACTS.md](../FACTS.md) 为准。

## CONFIRMED

- 查询命令为 `aa e1 00`，设备以 `0xe2` 返回当前七段完整状态。
- 设置命令为 `0xe3`，真实写帧总长 101 字节：`aa e3 61 00` 后跟 97 字节主体。
  `0x61` 不包含 LEN 后的特殊 `00` 分隔字节。
- 97 字节主体以 `c2 07 80 bb 00 00` 开头，表示七段和 48000 Hz；之后为七个等长的
  13 字节滤波器记录：

  ```text
  filter_type u8 | gain float32 LE | frequency float32 LE | Q float32 LE
  ```

- 七段中心频率为 125、250、500、1000、2000、4000、8000 Hz；filter type 为
  `0,1,1,1,1,1,2`，Q 为约 `0.707,2,2,2,2,2,0.707`。
- 改变一个频段时仍会发送包含全部七段的快照，不存在已确认的“只写一个频段”命令。
- 一次真实单变量抓包中，App 位置 `+7` 在 125 Hz 段写成 `+3.5 dB`，其余六段保持零。
- 当前测试设备恢复默认后，`e2` 读回七段均为 `0.0 dB`。
- 归档的同一次 EQ 拖动抓包包含两条 `0xe3` 写入；记录结束前没有出现
  `aa 00 02 e3 00`，也没有紧随其后的 `e2`。这直接证明该次会话不能用“已收到通用
  `e3` ACK”描述。

## OBSERVED

- HK One 2.5.4 前端把竖向滑杆配置为 `-12..+12`、整数间隔、吸附，共 25 个位置。
  它不是连续浮点滑杆。
- 前端默认使用倍率 2：滑杆位置除以 2 后才成为通常频段的协议增益。因此大部分频段的
  25 个位置对应 `-6.0..+6.0 dB`，每格 `0.5 dB`。
- 125 Hz 在负半轴另有前端补偿：除以 2 后再乘 `1.5`；正半轴不补偿。
- 滑杆拖动开始时立即提交一次；持续拖动期间通过 300 ms 门控限制提交频率；松手时无条件
  再提交最终位置。每次提交都沿 `changed → setEQ` 路径传递七段完整快照。
- App 的通用原生命令执行器支持按命令 ID 取消尚未执行的旧任务。这与“不依次回放每个
  已过期滑杆位置”的行为相容，但现有公开资料没有单独动态记录 EQ 队列的每次取消事件。
- 当前前端代码中，点击 EQ“重置”会先把七段编辑值全部归零，然后立即触发 `setEQ`；
  `✓` 的前端回调只关闭编辑面板。
- 早期人工交互曾观察到“不点击 `✓` 就没有完成重置”。它与上述静态代码观察冲突，二者
  都必须保留，不能用其中一个覆盖另一个。
- Home Assistant 集成 1.0.3 的现场日志中，一次 EQ 拖动产生了连续 GATT 会话：大多数
  会话在连接后约 4 秒开始断开，随后约 1.5 秒退避并重试，整体约每 8 秒出现下一轮连接。
  同期没有发现 Sendspin 主动移除经典蓝牙音频设备的对应事件。

## INFERRED

- 1.0.3 的 EQ 卡顿和连接风暴由两个行为叠加造成：它把滑杆经过的中间位置全部串行排队，
  并把 `0xe3` 当作会返回通用 ACK 的命令等待 4 秒。代码路径与代理日志时序一致，这是
  当前最有证据支持的根因解释。
- 对第三方控制器，更可靠的完成条件是：写 `e3` 后主动发送 `e1`，等待 `e2`，逐段比较
  返回快照与目标值；不能只依赖 ATT write 完成，也不能假定存在通用 `e3` ACK。
- 对网络蓝牙代理，合并已过期位置并只保留最新完整快照，比逐条复制 App 的中间更新更
  合适。300 ms 是 App 已观察到的节流尺度，不是协议强制的时序常量。

## UNKNOWN

- 当前固件是否在其他连接状态下偶尔返回 `aa 00 02 e3 00`，以及其他地区、SKU、固件的
  `e3` 确认行为是否一致。
- 125 Hz 的负端点是否会在真机上完整接受 App 算法给出的 `-9.0 dB`；目前端点缺少独立
  抓包和读回验证。
- “重置立即 `setEQ`”与“需要点击 `✓`”两项证据冲突的具体原因：可能在原生桥接时序、
  页面资源版本、退出方式或人工观察窗口，但目前无法定因。
- App 通用命令队列的同 ID 替换对 EQ 每一条拖动更新的实际取消比例。
- 快速交替调整两个不同频段时，App 和各固件如何处理正在传输的旧完整快照。

## SUPERSEDED

- **“App EQ 是连续、平滑的任意浮点调节。”** 已被 `-12..+12`、整数 interval 和吸附
  配置推翻；它有 25 个离散位置。
- **“App 的 `-12..+12` 就是协议中的 `-12..+12 dB`。”** 错误。通常频段先除以 2，
  对应 `-6..+6 dB`；125 Hz 负半轴还有额外补偿。
- **“每次 `0xe3` 都会返回通用成功 ACK。”** 现有抓包不支持这一说法，至少一次真实
  拖动的两条 `e3` 后均没有该 ACK。在线实现必须使用状态读回兜底。
- **“点击重置只改本地值，只有点击 `✓` 才调用 `setEQ`。”** 作为对 HK One 2.5.4
  当前前端代码的确定描述已经不成立；早期人工观察仍作为 UNKNOWN 冲突保留。
- **“前六段是 13 字节、最后一段是 12 字节。”** 是旧的错位解析。七段均为 13 字节，
  filter type 位于每段首字节。

## 对实现者的最低要求

1. UI 输入先量化到 App 的整数位置 `-12..+12`。
2. 每次构造完整七段快照，不能只根据一个频段生成残缺帧。
3. 同一批拖动请求应合并过期值，至少保证最终位置一定发送。
4. 写入后执行 `e1 → e2` 闭环，并以七段匹配作为成功判据。
5. 不把当前设备的范围、125 Hz 补偿或无 ACK 行为无条件推广到其他固件。
