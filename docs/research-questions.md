# 未确定但值得保留的问题

这些问题不应因初始发布清理而丢失，也不应在取得证据前写成产品能力。

## 高优先级

### `0x36` 状态机

已看到 `01/02/09`，且一次真实 A2DP 连接前后都保持 `01`。需要同步记录 BLE 通知、
Android/BlueZ HCI 连接状态、App 产品匹配阶段和物理音频行为，建立按上下文分组的状态表。

### EQ App 标尺与跨固件兼容

`0xe2/0xe3` 的特殊分隔字节、长度、七段结构和 filter type 已经由多份帧逐字节复核。
App 2.5.4 的 `-12..+12` 档位及通常 `0.5 dB` 映射已从前端实现确认；仍需实抓复核
125 Hz 负半轴的 `1.5x` 补偿端点，以及其他固件是否使用相同固定频率/Q/mode。上线写控制
前应先读当前状态，避免把未知固件的结构强行覆盖。

### 多 GATT 客户端

Android/BlueZ 双向顺序对照已确认：第二条物理链路和服务枚举有时可以共存，但第二端
CCCD 订阅在两轮 Android-first 实验中失败；BlueZ-first 时 Android 两轮均在连接阶段返回
通用 `status=133`。实际链路释放后 BlueZ 很快恢复，但密集重试还出现过一次短暂的双端
连接失败。仍需补充两套 BlueZ 客户端和官方 App 对照，区分通知槽数量、主机栈差异、
重试退避和 App 自身策略，并保存空口/HCI reason code；ATT 写完成不能代替应用层 ACK。

### App 产品匹配

`aa f5 02 01 1e`、后续递减通知和 `0x09` 很可能属于产品匹配状态机，但参数单位、超时、
确认命令和持久化位置未知。该流程包含物理确认，不应在默认工具中自动化。

## 中优先级

- 自动关闭计时的完整“活动”定义；灯效写已确认重置、只读查询已确认不重置，仍需覆盖
  A2DP/AUX/其他 BLE 写入及断电保持；
- 重命名写帧已确认；仍需验证经典蓝牙广播名、平台缓存和断电持久化；
- 125 Hz 负半轴的 App `1.5x` 补偿在 `-9 dB` 端点的真实设备复核；
- Android、Windows 和 BlueZ 的 AVRCP UI 百分比映射，以及与 BLE 任意整数音量的同步；
- A2DP/AUX 自动优先级、静默回退和断开超时；
- BLE 常连接是否改变休眠时序；已确认计时归零时 GATT 仍可能可达，且媒体动作 ACK 不会
  重启计时，仍需区分不同固件和更长时间后的广播行为；
- `0x43` 未知字段、`0xa2` 和设备信息字段的完整语义；
- 灯效颜色参数 `0..100` 到实际 LED 色彩空间的映射；
- 设置经过真正断电后的持久化行为。

OTA 和固件传输不属于本仓库研究范围，不列为待解决问题。

## 兼容性

- 其他地区、SKU、Wi-Fi 版和未来固件是否使用相同 UUID/帧；
- `0x184F`、`e49a1800...`、`0xFDDF` 的实际用途；
- 两套 Intel/WinRT 失败的必要条件，及其与控制器、驱动、缓存和会话生命周期的关系；
- 不同平台在匿名 Fast Pair 广告阶段能否可靠取得当前可连接 RPA。

## 硬件未知

内部 SoC、是否使用 Espressif 芯片及各芯片职责均未知。服务 UUID 不能作为芯片厂商证据；
硬件结论需要拆机标记、监管资料或固件中的独立证据。
